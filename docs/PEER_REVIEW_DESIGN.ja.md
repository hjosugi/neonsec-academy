# チーム / ピアレビューモード — 設計

ステータス: **設計のみ（P5-009）**。MVP は単一ユーザー・ローカル専用・バックエンドなしのままです。本書は、
[SAFETY_BOUNDARIES.ja.md](SAFETY_BOUNDARIES.ja.md) の安全モデルを弱めずに将来ピアレビューを構築できるよう、
データモデル、UX、ルーブリック、プライバシー/安全ガードレールを定義します。

## 目標と非目標

目標:

- 学習者が信頼できる仲間に、問題・レポート・ラボ解説のレビューを依頼できる。
- 共有物はすべて公開安全にする: 合成スコープのみ、端末外に出る前にマスキングする。
- フィードバックを実行可能にする: 箇所に紐づくコメント、具体的な提案、採点付きの承認、明示的な安全フラグ。

非目標:

- MVP でのホスト型アカウント、リアルタイム共同編集、テレメトリ。
- フルバックアップ、Evidence Vault のメモ、提出したフラグ、回答、ミスノートの共有。
- 実在の組織・実ターゲット・実インシデントを含むもののレビュー。

## ユースケース

| # | アクター | ユースケース | 結果 |
|---|---|---|---|
| U1 | 学習者 | ポートフォリオに載せる前にラボレポートを学習仲間と共有する。 | レビュアーが影響の表現改善を提案し、学習者が採用する。 |
| U2 | 学習者 | 作成した問題のトラップの質と解説の正しさをメンターに確認してもらう。 | メンターがルーブリック採点付きで承認し、問題をパックとして出力する。 |
| U3 | 学習グループ | IR トラックで作ったタイムラインを順番にレビューする。 | 各メンバーがタイムライン行やセクションに紐づくコメントを受け取る。 |
| U4 | モデレーター | 共有パッケージ内の実在ホスト名や実働ペイロードに気付く。 | 安全フラグ（blocker）で、作者が修正して再マスキングするまで非表示にする。 |
| U5 | 学習者 | 該当しないコメントに返信または却下する。 | スレッドに解決状態が表示され、却下も履歴に残る。 |

## ロール

- **作者**: パッケージを作成し、コメントに回答し、提案を採否し、スレッドを解決する。
- **レビュアー**: コメント、提案、ルーブリック採点付き承認、安全フラグの提起。
- **モデレーター**: レビュアーの権限に加え、パッケージの非表示/再表示と安全フラグのクローズ。

ID は仮名のハンドル（2〜40 文字）です。本名・メール・勤務先名は不要で、本文に書かれた場合はマスクされます。

## データモデル

`docs/schemas/` に JSON Schema を持つ 2 つの JSON ドキュメント:

- [`peer-review-package.schema.json`](schemas/peer-review-package.schema.json) — レビュー対象のマスク済みスナップショット。
- [`peer-review-comment.schema.json`](schemas/peer-review-comment.schema.json) — コメント、提案、承認、安全フラグの 1 件。

```text
ReviewPackage 1 ── * ReviewComment
ReviewComment 0..1 ── * ReviewComment（parentId による返信）
ReviewPackage * ── 1 元アーティファクト（Question | Report | ラボ解説）、ローカル ID でのみ参照
```

### レビューパッケージ

| フィールド | 説明 |
|---|---|
| `format`, `version` | `neonsec-review-package`、`1`。 |
| `id` | `rp-…` 識別子。 |
| `kind` | `question`、`report`、`lab-writeup`。 |
| `author.handle` | 仮名のハンドル。 |
| `title`, `content` | 公開安全エクスポーター（ポートフォリオと同じパイプライン）が生成した Markdown。生のバックアップや Vault メモは不可。 |
| `masking` | `publicSafe: true`、`redactions`、`sensitiveHits: 0`、`checklistConfirmed: true`。これ以外ではパッケージを作れない。 |
| `state` | `draft → in-review → changes-requested ↔ in-review → approved`。blocker の安全フラグで任意の状態から `hidden`。 |
| `reviewers` | 最大 5 つのハンドル。 |

### レビューコメントのスキーマ

| フィールド | 説明 |
|---|---|
| `id`, `packageId`, `parentId` | スレッド。トップレベルは `parentId` が null。 |
| `kind` | `comment`、`suggestion`、`approval`、`safety-flag`。 |
| `author` | `handle` と `role`（`author`、`reviewer`、`moderator`）。 |
| `anchor` | `section`（question、explanation、summary、scope、methodology、finding、remediation-plan、appendix、writeup）、任意の `findingId`、任意の短い `quote`（280 文字以内、マスク済み）。 |
| `body` | 1〜4000 文字の Markdown。保存時にマスク。 |
| `suggestion` | `suggestion` で必須: `replacement` と `accepted`（作者の判断までは null）。 |
| `rubric` | `approval` で必須: 正確性・証拠・明瞭さ・修正・安全性の 1〜4 点。 |
| `safetyFlag` | `safety-flag` で必須: `category`（real-target、credential、personal-data、attack-instructions、malware、non-public-info、other）と `severity`（`blocker` / `warning`）。 |
| `status` | `open`、`resolved`、`dismissed`。 |
| `createdAt`, `updatedAt` | エポックミリ秒。 |

## レビュールーブリック

承認では各基準を 1〜4 で採点します。少なくとも 1 人のレビュアーが全基準 3 以上で承認し、未解決の安全フラグが
無いときにパッケージは **approved** になります。

| 基準 | 1 — 要改善 | 2 — 部分的 | 3 — 十分 | 4 — 模範的 |
|---|---|---|---|---|
| 正確性 | 分類や結論が誤り。 | ほぼ正しいが重要な点が誤り。 | 正確で具体的。 | 正確・具体的で、他の選択肢が誤る理由も説明。 |
| 証拠 | 引用なし。 | 曖昧な参照。 | 正確なアーティファクト行や Vault 項目を引用。 | 証拠を引用し確信度も述べる。 |
| 明瞭さ | 追いにくい。 | 努力すれば理解できる。 | 想定読者に明確。 | 明確・簡潔・構成が良い（エグゼクティブサマリーが先頭）。 |
| 修正 | なし。 | 一般論。 | 検証方法付きの具体的な修正。 | 優先度付きの修正と検知・予防。 |
| 安全性 | 実ターゲット、秘密、攻撃の実行手順を含む。 | 境界的な表現。 | 合成スコープを明記し機密情報なし。 | 合成スコープが明確で全体が防御的な構成。 |

安全性が 1 の場合は `safety-flag` コメントを必ず付けます。

## UX フロー

1. **レビュー依頼**（Report Builder、Question Editor、ラボ詳細）: 「Request review」でポートフォリオと同じ
   公開安全プレビュー（機密プレースホルダーチェック、置換数、プライバシーチェックリスト）を開きます。チェックが
   クリーンで全項目を確認するまでパッケージを作成できません。
2. **レビュー画面**: 左列にセクションアンカー付きのマスク済み Markdown、右列に種類・状態で絞り込めるスレッド。
   テキスト選択でアンカー付きコメントや提案を作成。承認ダイアログは 1〜4 の選択付きルーブリック表を表示します。
3. **作者の受信箱**: セクション別の未解決スレッド。提案は差分プレビューと採用/却下。採用するとローカルの元データに
   反映し、次のバージョン共有前に再マスキング・再チェックします。
4. **安全フラグ**: 誰でも提起可能。`blocker` は作者とモデレーター以外に対して即座に `hidden` にします。作者は
   ローカルで修正して再マスキングし、モデレーターがフラグを解決します。
5. **レビュー終了**: 作者が承認済み（ルーブリック条件を満たす）にするか取り下げます。取り下げたパッケージは共有
   ストレージから削除されます。

## プライバシーと安全のガードレール

- **公開安全のみ**: パッケージは公開安全エクスポーターのパイプライン（`redactSensitiveText` と real-TLD モードの
  `scanSensitiveText`）でのみ生成し、`masking.sensitiveHits` は 0 でなければならない。
- **生データ禁止**: バックアップ、Evidence Vault のメモ、提出フラグ、試行履歴、ミスノート、非公開モードの
  エクスポートはパッケージにできない。
- **全箇所でマスキング**: コメント本文・引用・提案も保存前に同じマスキングを通し、マスキング後も機密値が残る
  コメントは拒否する。
- **安全監査**: `lab-writeup` と作成問題のパッケージにはラボ安全監査ルール（禁止ターゲット/行為、ペイロード、
  ツールコマンド、実在マルウェアへの言及）も適用し、ブロッカーがあれば共有不可。
- **仮名性**: ハンドルのみ。プロフィールにメール・本名・勤務先名を持たない。
- **最小限の公開**: レビュアーはパッケージごとに招待（最大 5 人）。公開一覧は無い。
- **保持期間**: レビュー終了時または 90 日後にパッケージとコメントを削除。
- **モデレーション**: blocker フラグは即時非表示。モデレーターは作者の内容を編集できず、非表示とフラグ解決のみ可能。
- **永久に対象外**: 実案件・実インシデント・実ターゲット・NDA 対象のレビュー。

## 将来の実装メモ

- ホスト型サービスの前に、ファイルベースの交換（`neonsec-review-package` JSON とコメント JSON のエクスポート/
  インポート）から始め、アプリをバックエンドなしに保つ。
- インポート時に `docs/schemas/` のスキーマで両ドキュメントを検証し、ローカルでマスキングと安全監査を再実行する。
  受け取ったパッケージは信頼しない。
- 既存モジュールを再利用: `lib/portfolio.ts`（公開安全ビルド）、`lib/contentSafety.ts`（マスキングと検出）、
  `lib/labSafetyAudit.ts`（コンテンツルール）、`lib/reportQuality.ts`（ルーブリック横の品質チェック）。
